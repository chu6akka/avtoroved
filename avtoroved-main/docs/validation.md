# Валидация детектора ошибок

Оценка штатного пути детектора программы — собственные правила пунктуации
(`analyzer/punct_checker.py`) + LanguageTool (строго локальный режим) +
слой фильтрации (`protocol/detector_filter.py` с текущим конфигом) — на
открытых корпусах исправления ошибок.

## Датасеты

`ai-forever/spellcheck_punctuation_benchmark` (HuggingFace):

- **RUSpellRU** — тексты соцсетей с естественными ошибками (test, 2008 пар);
- **MultidomainGold** — 7 доменов: новости, литература, соцсети, отзывы,
  субтитры, веб, стратегические документы.

Пары «source (с ошибками) ↔ correction (эталон)»; корпуса открытые и не
являются материалами дел, поэтому прогон через локальный LT допустим.

## Методика подсчёта

Скорер — **встроенный пословный, приближение** (SAGE в окружении не
установлен): эталонной ошибкой считается токен, в котором source и
correction расходятся (выравнивание difflib); предсказанием — токен,
накрытый срабатыванием детектора после фильтра. Категории расхождений:
SPELL (буквенные), PUNCT (знаки), CASE (регистр), YO (ё/е).

## Как воспроизвести

```bash
# полный прогон (нужен интернет для загрузки корпусов; Java для LT)
python scripts/validate_detector.py --limit 150 --out docs/validation.md

# без LanguageTool (только собственные правила)
python scripts/validate_detector.py --limit 150 --no-lt
```

Скрипт логирует: версию/режим LanguageTool, хэш конфига фильтра, имя и
объём датасета, дату прогона — всё попадает в таблицу ниже.

При установленной библиотеке SAGE (`pip install sage` c GitHub ai-forever)
скрипт автоматически использует её загрузчик датасетов и скорер ruspelleval
вместо приближённого.

## Честные оговорки

1. Корпуса покрывают **орфографию и пунктуацию** (и частично регистр/ё).
   Грамматические и лексико-фразеологические ошибки бенчмарком не
   покрываются — корпус RULEC-GEC доступен по запросу автору и в этот
   прогон не входит.
2. Детектор программы — **сигнализатор для эксперта**, а не автокорректор:
   его задача — предъявить кандидатов с фрагментами, решение остаётся за
   экспертом. Поэтому recall на корпусах орфографии заведомо ограничен
   составом правил LT, а precision важнее recall.
3. Пословный скорер — приближение: многословные замены и вставки знаков
   учитываются упрощённо (вставка вешается на соседний токен).
4. Фильтр ложных срабатываний (`detector_filter.json`) настроен на снижение
   шума в экспертном контуре; часть подавленных правил снижает recall на
   бенчмарке — это осознанный компромисс, управляемый конфигом.

### Интерпретация

- **RUSpellRU** (соцсети, «живые» ошибки): орфография ловится уверенно
  (SPELL F1 = 0.727 при precision 0.74) — это основной рабочий сценарий
  детектора в экспертизе. Пунктуация слабее (F1 = 0.26): часть
  пунктуационных правил намеренно подавлена/понижена фильтром как шумная,
  плюс пословный скорер грубо учитывает вставки знаков.
- **MultidomainGold** (сборный корпус: официальные документы, литература,
  веб): низкая precision (0.09) объясняется профилем корпуса — большая
  доля эталонных правок это регистр и ё (90 из ~200 gold-позиций), которые
  наш детектор кандидатами не считает, а LT при этом активно флагует
  термины, имена собственные и разговорные формы, не входящие в эталон.
  Для экспертного контура такие срабатывания уходят под переключатель
  «низкая надёжность» и в словарь исключений — на бенчмарке это выглядит
  как FP, в программе — как скрытые кандидаты.
- Вывод для защиты: детектор пригоден как **сигнализатор орфографических
  кандидатов** (precision ~0.7 на живых текстах); пунктуационные и
  доменные срабатывания требуют экспертной проверки — что и отражено в
  протоколе пометкой «требует проверки» и фильтром надёжности.
