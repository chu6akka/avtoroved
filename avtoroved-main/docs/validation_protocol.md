# Протокол корпусной валидации «Автороведа»

## Назначение и границы

Контур `validation/` проверяет обнаружение кандидатов признаков, воспроизводимость, вспомогательные тематический и стилевой слои, прохождение экспертного отбора и трудозатраты. Он **не измеряет точность вывода об авторстве**, не подменяет экспертное решение и не изменяет production-пороги.

Проверяемая конфигурация заморожена: ThemeEngineV2 использует `cointegrated/rubert-tiny2` revision `e8ed3b0`, floor 0,44, margin 0,08, минимум один сегмент и cap 4; StyleEngineV2 — F_HYBRID, floor 0,12, margin 0,08, две семьи и weak threshold 0,14. Снимок сохраняется в каждом прогоне.

## Структура данных и обезличивание

- `validation/corpus/` — тексты, `manifest.jsonl`, пары `cases.json`;
- `validation/annotations/` — исходные экспертные аннотации, gold тем/стилей и записи времени;
- `validation/schemas/` — формальные JSON Schema;
- `validation/results/<run_id>/` — неизменяемый пакет одного прогона;
- `validation/reports/<run_id>.md` — копия отчёта.

Имена авторов и экспертов запрещены: используются псевдонимы `A001`, `E001`. Ожидаемое отношение пары предназначено только для организации выборки и не передаётся анализатору. Его точность не является метрикой системы. Анализатор получает только `BlindDocument`: текст, идентификатор документа и технические метаданные. Автор, ожидаемое отношение, gold и экспертные решения в объекте отсутствуют конструктивно.

## Формирование корпуса и разделение выборок

1. `DEVELOPMENT` допускает разработку форматов и тестовых фикстур.
2. `PILOT` используется для первой проверки реального корпуса и поиска дефектов протокола. Результаты пилота не являются финальными.
3. `VALIDATION` замораживается до запуска. После просмотра результатов запрещено менять параметры и повторно представлять ту же выборку как независимую валидацию.

Разделение выполняют по псевдониму автора, а не по документам. Один автор и один точный текст не должны попадать одновременно в development/pilot и validation. `check_corpus.py` проверяет эти утечки, SHA-дубли, пустые и слишком короткие документы, обязательные метаданные и SHA256.

`input_sha256` — SHA-256 точных байтов входного файла, вычисляемый единым
`validation.io.sha256_file` через `Path.read_bytes()`. BOM, пробелы, завершающий
перевод строки и иные байты не нормализуются. Для текстов corpus в репозитории
Git принудительно сохраняет и выдаёт LF, чтобы одни и те же входные байты были
воспроизводимы на Windows, Linux и macOS.

Поставляемый `validation/corpus/demo` — только синтетическая демонстрация из шести документов трёх условных авторов. Она относится к DEVELOPMENT, не является пилотной/дипломной выборкой и не служит доказательством качества.

## Экспертная разметка и gold

Разметка разделяет `present` (наблюдается ли признак) и `accepted` (принял ли эксперт факт в карту). Экспертное принятие не превращается автоматически в gold обнаружения. Исходные аннотации сохраняются без перезаписи. Для нескольких экспертов рассчитываются процент согласия и Cohen’s kappa при достаточной опоре. Допускается отдельная адъюдикация; источник gold фиксируется как `CONSENSUS`, `ADJUDICATED` или `SINGLE_EXPERT`. Идентификационная ценность автоматически не назначается.

## Метрики

Для каждого реализованного признака считаются TP, FP, FN, precision, recall, F1 и support; малая опора помечается `insufficient_support`. Метрики агрегируются по смысловой, текстологической, лексической, стилистической, синтаксической, морфологической, орфографической, пунктуационной и психолингвистической группам там, где автоматизация реализована.

- `AUTO`/`AUTO_DETECTABLE`: полные метрики обнаружения;
- `CANDIDATE_ONLY`: отдельные метрики обнаружения кандидатов;
- `EXPERT_ONLY`: `not_automated_by_design`, без ложного FN.

Темы: top-1, micro precision/recall/F1, macro F1, recall смешанных тем. Стили: те же multi-label метрики, abstention rate, recall смешанного стиля и отдельные publicistic/conversational. Для длинных текстов допускаются document- и segment-level gold, включая переходы. Эти показатели вспомогательны и не доказывают тождество автора.

## Хронометраж

Сравниваются только парные записи одного case/expert/stage в режимах `MANUAL` и `ASSISTED`. Для непарных наблюдений процент экономии не вычисляется. Выводятся mean, median, min и max абсолютной экономии времени. `session_order` обязателен; порядок режимов следует контрбалансировать.

## Запуск

Из каталога `avtoroved-main`:

```powershell
python -m validation.check_corpus validation/corpus/demo
python -m validation.run --corpus validation/corpus/demo --annotations validation/annotations/demo --output validation/results --mode pilot --synthetic-demo
```

Для реального прогона `--synthetic-demo` не используется. Каждый `run_id` создаёт отдельную папку и никогда не перезаписывается. Сохраняются сырые результаты, JSON/CSV, Markdown-отчёт, версии, git commit, снимок конфигурации и SHA256 входа, аннотаций, конфигурации и выходов.

## Интерпретация и ограничения

Пилот проверяет процедуру, а не даёт финальный результат. Низкая полнота CANDIDATE_ONLY ограничивает автоматический поиск, но не доказывает отсутствие признака. EXPERT_ONLY оценивается через экспертный процесс. Любое изменение движка после validation требует новой независимой замороженной выборки.
