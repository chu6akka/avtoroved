# Состав модулей: идентификационное ядро и исключённый функционал

> Статус данных активного контура определяется моделью ролей, описанной в
> [`feature_model.md`](feature_model.md). Сохранение аналитического модуля в
> составе продукта не означает, что каждое его измерение является частным
> идентификационным признаком. В методическое сравнение допускаются только
> принятые экспертом записи `METHOD_FEATURE`; метрики, evidence и общие навыки
> остаются доступны эксперту в собственных ролях.

Экспертная квалификация не образует второго конвейера: созданные экспертом
записи остаются в `feature_candidates`, а решения — в существующих
`feature_decisions`/`features`. Новые событийные таблицы хранят только
проверяемые основания, связи с evidence и историю оценок; правила допуска
описаны в [`expert_feature_qualification.md`](expert_feature_qualification.md).

Документ обосновывает ревизию функционала при переориентации программы с
«универсального NLP-инструмента» на **идентификационную автороведческую
экспертизу** (глава 2 ВКР). Критерий отбора: функция входит в ядро, только
если она (а) порождает признак, который эксперт принимает в карту признаков,
либо (б) обслуживает одну из четырёх стадий методики (пригодность →
раздельное → сравнительное → оценка и вывод; Рубцова и др., 2007, с. 80–85).

Принцип исключения: **ничего не удалено физически** — модуль остаётся в
репозитории, но выводится из UI-процесса (механизм `archived_pages` в
`config.json`) и из активного пайплайна. Исключённое — материал раздела
«перспективы развития», а не мусор.

### Оговорка о заимствовании метода Огорелкова

У И.В. Огорелкова аппарат применён к **диагностической** задаче — установлению
пола автора текста. В настоящей программе заимствован только инструментальный
аппарат: закрытый перечень служебных лексико-грамматических классов и
ipm-нормирование по частотному словарю НКРЯ (Ляшевская, Шаров). Диагностические
модели пола не воспроизводятся и находятся вне идентификационного ядра; модуль
выдаёт исключительно наблюдаемые частоты как кандидатов признаков, решение об
их принятии выносит эксперт. Ни агрегированной «меры сходства» по служебной
лексике, ни автоматических выводов программа не формирует: единый числовой
индекс близости был бы скрытым выводом об авторстве.

## Сетевые зависимости — итог

В протокольном контуре сетевых обращений **нет**: LanguageTool — только
локальный сервер (публичный API отключён на уровне `profile.py`),
Яндекс.Спеллер исключён, обращений к api НКРЯ в коде не существует
(частотность — локальный словарь), эмбеддинги не используются. Сетевые
операции остались только в явных сервисных действиях по команде
пользователя: обновление словарных баз (`lexicon_update`, с бэкапом и
версией) и внешние словари в карточке токена (открываются в браузере по
клику, текст никуда не передаётся).

## Перспективы развития (исключённое)

GigaCheck (аутентичность текста), диагностический профиль (пол/возраст),
тональность как диагностический маркер, семантическое расширение словарей
(rusvec/navec), SBERT-сходство, Яндекс.Спеллер как дополнительный движок
детектора (через тот же `detector_filter`) — всё сохранено в коде и может
быть возвращено: вкладки — правкой `archived_pages`, вызовы — по
комментариям-ссылкам на этот документ.
